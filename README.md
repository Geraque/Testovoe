# Тестовое задание: разработчик интеграций

Решения двух задач: распределение накладных по заявкам ГУ-12 и сверка складского журнала с документами 1С. Исходное условие сохранено в `Тестовое_задание.docx`, входные файлы в `data/` не изменены.

## Как запустить

Нужен Python 3.10 или новее. Используется только стандартная библиотека, установка пакетов не требуется. Из каталога с этим README:

```bash
python main.py
python -m unittest discover -s tests -v
```

На Windows вместо `python` можно использовать `py -3`. Результаты прогона уже приложены: [result_z1.json](result_z1.json) и [result_z2.json](result_z2.json). Повторный запуск перезаписывает их.

Другие каталоги можно передать явно:

```bash
python main.py --data-dir data --output-dir output
```

По умолчанию пути считаются от расположения `main.py`, поэтому запуск по абсолютному пути работает из любого каталога. Явно переданные относительные пути считаются от текущего рабочего каталога. Ошибка чтения или обработки данных завершает программу с кодом 1 и сообщением в stderr. Обе задачи рассчитываются до начала записи результатов.

## Бизнесовые решения и их обоснование

Ниже описаны выбранные трактовки там, где условие оставляет варианты. Правила, прямо заданные в условии, вынесены отдельно: например, заполнение просроченной заявки — требование, а способ распределения разницы округления — принятое решение.

### Почему ошибка входных данных останавливает весь расчёт

При обнаружении некорректных данных выбрана остановка всего запуска. Например, обратный период заявки не исправляется автоматически, повторяющийся ID не удаляется, а остаток на счёте `10.07` без контрагента не записывается на неизвестного подрядчика.

Альтернатива — пропустить проблемную строку и обработать остальные. Но её исключение может изменить результат: без одной заявки вагоны попадут в другие заявки или в «без заявки», а без одной выдачи доступный остаток будет завышен. Программа не знает, какое исправление соответствует реальной операции, поэтому не должна выдавать такой расчёт за полный.

Можно было бы остановить только отдельного клиента и продолжить остальных: в первой задаче очереди клиентов действительно независимы. Однако это изолирует вычисления, но не подтверждает качество оставшейся выгрузки. Обнаруженная ошибка не доказывает, что все данные неверны, но даёт основание проверить источник: тем же способом могли быть повреждены и другие строки, в том числе так, что формальные проверки этого не заметят. Автоматически считать оставшуюся часть достоверной оснований нет.

Поэтому выбран общий отказ от расчёта до исправления входа. Цена решения — одна ошибка блокирует и корректные данные, включая вторую задачу. Частичный результат был бы допустим при отдельно согласованных правилах проверки выгрузки и явном отчёте о том, какие клиенты или операции исключены; такого режима в задании нет.

При ошибке чтения или расчёта программа завершается с кодом 1 до записи обоих результатов. Файлы от предыдущего успешного запуска, если они есть, остаются на месте и не являются результатом неудачного запуска. Это не гарантия совместной записи файлов при сбое диска: ошибка непосредственно во время сохранения может оставить только часть нового вывода.

Предусмотренные условием ситуации не считаются такими ошибками: накладная без клиента попадает в `bez_klienta`, отсутствие документа — в `ne_najdeno`, несколько кандидатов — в `neodnoznachno`. Пустой контрагент в остатках не на счёте `10.07` допустим: такие строки относятся к МОЛ.

### Задача 1 — распределение массы и округление

Выбрано сохранение общей массы накладной с точностью до 0,1 т. Если 1 т распределить на три части по одному вагону, точная доля каждой — `0,333…` т. Независимое округление даст `0,3 + 0,3 + 0,3 = 0,9` т: владелец данных увидит недостающие 0,1 т, хотя никакого движения материала не было.

Можно отнести всю разницу на последнюю часть. Это проще, но она будет постоянно накапливать поправки; при большом количестве мелких частей и независимом округлении остальных такая поправка может даже сделать её отрицательной. Другой вариант — увеличить точность хранения, но в результате по условию требуется шаг 0,1 т, и вопрос согласования итогов всё равно остаётся.

Поэтому используется метод наибольших остатков. Сначала каждой части выделяется целое количество десятых тонны без превышения её пропорциональной доли, затем оставшиеся десятые получают части с наибольшими дробными остатками. При равенстве приоритет у более ранней части: дополнительного критерия в задании нет.

В примере результат будет `0,4 + 0,3 + 0,3 = 1,0` т. Для учёта предпочтительнее явно распределить разницу округления, чем заставлять владельца искать пропавшие 0,1 т. Это учётные доли, а не утверждение о разной физической массе одинаково загруженных вагонов. Отдельная доля может отличаться от обычного округления до ближайшей десятой, зато сумма сохраняется и отрицательных частей нет. Такое согласование округления — наше допущение, а не прямо заданный способ из условия.

Если входная масса точнее 0,1 т, сначала общий итог округляется по `ROUND_HALF_UP`, затем распределяется. Сохранение суммы в этом случае относится к округлённому итогу: например, 1,25 т превращаются в 1,3 т. Точную исходную массу с большей разрядностью невозможно всегда сохранить суммой частей, кратных 0,1 т.

### Задача 1 — даты, равенство приоритетов и представление результата

**Границы периода.** Начальный и конечный день включаются целиком. Альтернатива — считать конец датой в 00:00 и исключать последующие отправки этого дня. Она не выбрана, поскольку в исходных данных границы задаются днями без времени: период по 30 сентября должен включать отправку 30 сентября вечером. Время поступления заявок и отправки накладных учитывается при сортировке.

**Полное равенство приоритетов.** При одинаковых начале периода и времени поступления заявки сохраняется входной порядок. То же правило действует при одинаковом времени отправки накладных. Можно было бы добавить иной критерий или отклонить равенство как ошибку, но дополнительный бизнес-приоритет не задан, а использование номера заявки прямо запрещено. Входной порядок позволяет обработать такие строки без придуманного преимущества одной заявки; при перестановке равнозначных строк результат может измениться.

**Превышение.** На пару «заявка — накладная» выводится одна строка: `vagonov` и `massa_t` содержат общий объём, `sverh_zayavki` — количество вагонов из этого объёма сверх заявки, а не флаг. Например, B2002 в заявке 0000700050 представлена 10 вагонами и 570 т, из которых 2 вагона сверх. Альтернатива — отдельные строки обычной части и превышения — позволяла бы видеть их массы отдельно, но такого требования нет, а повтор одного номера усложняет чтение. Объединение сохраняет требуемые сведения: количество в пределах квоты равно `vagonov − sverh_zayavki`. Части объединяются до распределения массы, чтобы её округление не зависело от внутреннего разделения на обычные и сверхнормативные вагоны. Между разными заявками накладная по-прежнему может делиться.

**Пустые значения.** Отсутствующий, пустой или `null` клиент накладной означает `bez_klienta`: разные способы обозначить отсутствие клиента не должны менять её судьбу. Отклонять такие накладные было бы неверно, поскольку для них прямо предусмотрен раздел результата. У активной заявки клиент обязателен: без него невозможно определить, чьи накладные она вправе принимать. Активные заявки без накладных выводятся с пустым списком, чтобы отличать отсутствие распределения от исключения заявки; группы `bez_zayavki` создаются только при наличии остатков.

### Задача 2 — повторяющиеся позиции

Повторные строки одного кода суммируются внутри одной записи журнала или одного документа 1С перед сравнением. Например, `Н-001: 2` и `Н-001: 3` считаются равными одной строке `Н-001: 5`. Разные документы и записи между собой не объединяются.

Альтернатива — сравнивать каждую строку с учётом повторений, разрешая только перестановку. Выбрано суммирование, потому что для этой сверки значимы материал и общее количество, а не способ разбиения на строки. Отдельных признаков партий или иных свойств строк в данных нет. Независимость от порядка прямо задана условием, а возможность объединять одинаковые коды — дополнительная трактовка.

### Задача 2 — конкуренция записей за документ

Записи обрабатываются по дате, затем по числовому ID; кандидаты ищутся среди ещё не использованных документов. Если у двух записей один общий подходящий документ, первой связывается более ранняя запись. Вторая при отсутствии других свободных кандидатов попадает в `ne_najdeno`. При равной дате ID задаёт воспроизводимый порядок, но не доказывает хронологию фактических выдач.

Альтернатива — оставить обе записи несвязанными и вынести конфликт на ручную сверку. Она осторожнее в отношении принадлежности документа. Также можно было бы искать соответствия сразу для всего набора записей. В текущем решении выбран приоритет старой выдачи как явное допущение: сначала закрывается более раннее неподтверждённое движение, а документ не используется повторно. Условие не определяет такой приоритет; более ранняя дата сама по себе не доказывает, что документ относится именно к этой записи. Перед рабочим внедрением это правило нужно согласовать.

Если у одной записи несколько кандидатов, связь не создаётся — это прямое требование. Дополнительно выбрано не резервировать документы и не пересматривать эту запись после обработки следующих. Иначе пришлось бы либо лишать другие записи доступных документов без подтверждённой связи, либо вводить повторное связывание по косвенным исключениям. Список неоднозначности отражает кандидатов на момент обработки; один из них может позже связаться с другой записью. Это ограничение последовательного алгоритма, а не окончательный список свободных документов.

### Задача 2 — возвраты и статусы

Для `vozvrat` не задан соответствующий вид документа 1С. Поэтому активный возврат остаётся несвязанным, входит в `ne_najdeno` и корректирует остатки. Можно было бы исключить его из отчёта о поиске документов, но тогда фактическое движение без подтверждения в 1С было бы менее заметно. Связывать возврат с передачей подрядчику нельзя: это противоположные операции.

Непустой `kontragent_id` у возврата означает возврат от подрядчика, иначе — от своих. Альтернатива — восстанавливать карточку через `iskhodnaya_id`, но для этого нужны правила проверки исходной выдачи и полноты истории. Они не заданы, поэтому используются реквизиты самого возврата. `iskhodnaya_id` связывает записи журнала и не подтверждает проведение возврата в 1С, даже если исходная выдача уже связана с документом.

Только статус `vydano` участвует и в связывании, и в корректировке остатков. Для связывания это прямо указано; для расчёта выбрана та же граница. Альтернатива — вычитать также черновые или отменённые несвязанные записи — создала бы движение материала без подтверждения фактической выдачи.

### Задача 2 — остатки и границы выгрузки

Повторяющиеся строки остатков суммируются по МОЛ/коду или контрагенту/коду. Отсутствующая пара начинает с нуля: так несвязанная выдача не исчезнет из расчёта только из-за отсутствия исходной строки. Альтернатива — считать отсутствие пары ошибкой — отвергала бы и новые движения по ранее нулевой позиции. Это допущение предполагает, что отсутствие строки в снимке означает нулевой остаток, а не неполную выгрузку.

Отрицательные остатки сохраняются. Можно было бы обнулить их или остановить расчёт, но это скрыло бы величину расхождения либо не позволило бы получить отчёт для сверки. Отрицательное значение показывает результат заданной формулы, а не физическую возможность выдать отрицательное количество. Нулевые строки исключаются только у подрядчиков, как указано в условии.

Расчёт выполняется по всему переданному снимку. Отбор по сегодняшней дате или предполагаемому периоду не выбран: дата отсечения не задана, а такой фильтр мог бы отбросить старую незакрытую выдачу. Неизвестный тип активного движения журнала вызывает ошибку — без него нельзя определить знак корректировки. Неподдерживаемый вид документа 1С не является кандидатом, поскольку для него не задано соответствие; его влияние на исходные остатки уже входит в выгрузку.

### Правила, которые прямо следуют из задания

- Отозванные заявки исключаются; клиенты не смешиваются. Первая доступная заявка добирает вагоны и после конца периода, но будущая заявка их не принимает. Превышение попадает в последнюю заявку, период которой включает отправку.
- При связывании проверяются вид, МОЛ, карточка подрядчика, состав и количества. Окно даты включительно: от даты записи минус 2 календарных дня до плюс 14. Совпадения имени или ИНН недостаточно для объединения разных карточек.
- Связанные выдачи не корректируют остатки повторно. Несвязанные, включая неоднозначные, корректируют их по формуле задания. Это не устраняет возможное задвоение исходных фактов: спорные записи требуют ручной сверки.
- Счёт `10.07` относится к подрядчикам, остальные — к МОЛ.

## Технические решения

- Названия данных сохранены из задания: `zayavki`, `nakladnye`, `zhurnal`, `dokumenty`, `nomer`, `klient`, `kontragent_id`, `stroki`, `kol` и названия разделов результата. Обычно я придерживался бы принятого в проекте стиля, но здесь он заранее неизвестен. Поэтому выбрал исходную терминологию, чтобы при чтении файлов и кода не приходилось запоминать несколько названий одной сущности. Вспомогательные переменные и операции называются по-английски: `queue`, `parts`, `candidates`, `match_key`. Для вычисляемых значений используются отдельные точные имена: `available_wagons` — свободные места заявки, `unallocated_wagons` — ещё не распределённые вагоны накладной. Они не названы исходным `vagonov`, поскольку это разные величины.
- Алгоритмы отделены от файлового ввода-вывода: их можно проверить на небольших примерах без создания файлов. Входные словари не изменяются.
- Количества и масса рассчитываются через `Decimal`, чтобы двоичная погрешность `float` не влияла на сравнение и арифметику. Запятая в числе заменяется точкой, дробные JSON-числа сразу читаются как `Decimal`. Это средство реализации выбранных правил точности; способ распределения массы обоснован выше.
- На выходе числа преобразуются в `float` для стандартной сериализации JSON числами, а не строками. После этого арифметика не выполняется. Остатки не округляются до десятых: например, `11.41` сохраняется. Такое преобразование рассчитано на размеры и точность чисел задания, а не на произвольно длинные десятичные значения.
- Для `nachalo` и `konec` принимаются оба формата: `дд.мм.гггг` и `дд.мм.гггг чч:мм:сс`. Время проверяется на корректность, но при определении периода используются только календарные дни с включёнными границами. Например, `01.09.2026` и `01.09.2026 00:00:00` задают одну дату начала. Поля `postupila` и `data_otpravki` читаются как `дд.мм.гггг чч:мм:сс` с сохранением времени, даты второй задачи — как `гггг-мм-дд`.
- Проверяются уникальность номеров заявок/накладных и ID записей/документов, конечность чисел, допустимость количества вагонов, положительность строк движений и корректность периода заявки. Успешные проверки не гарантируют фактическую достоверность выгрузки; политика остановки при выявленной ошибке описана выше.
- Коды, клиенты, МОЛ и ID контрагентов сравниваются точно. Документы индексируются по виду, МОЛ, карточке и нормализованному составу, после чего проверяются дата и занятость документа. Справочники использованы для анализа данных; в расчёте достаточно кодов и ID из движений.
