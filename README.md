# Тестовое задание: разработчик интеграций

Решения двух задач: распределение накладных по заявкам ГУ-12 и сверка складского журнала с документами 1С. Исходное условие сохранено в `Тестовое_задание.docx`, входные файлы в `data/` не изменены.

## Как запустить

Нужен Python 3.10 или новее. Используется только стандартная библиотека, установка пакетов не требуется. Из каталога с этим README:

```bash
python main.py
python -m unittest discover -s tests -v
```

На Windows вместо `python` можно использовать `py -3`. Результаты прогона уже приложены: [result_z1.json](result_z1.json) и [result_z2.json](result_z2.json). Повторный запуск перезаписывает их.

Другие каталоги можно передать явно:

```bash
python main.py --data-dir data --output-dir output
```

По умолчанию пути считаются от расположения `main.py`, поэтому запуск по абсолютному пути работает из любого каталога. Явно переданные относительные пути считаются от текущего рабочего каталога. Ошибка чтения или обработки данных завершает программу с кодом 1 и сообщением в stderr. Обе задачи рассчитываются до начала записи результатов.

## Бизнесовые решения и их обоснование

### Ошибки входных данных

Некорректные данные останавливают весь запуск. Пропуск строки может изменить распределение вагонов или остатки, а программа не знает, какое исправление соответствует факту. Можно изолировать ошибку одного клиента, но это не подтверждает качество остальной выгрузки: обнаруженный дефект даёт основание проверить источник целиком. Поэтому выбран полный отказ от расчёта, хотя он блокирует и корректные данные. Предусмотренные заданием случаи — без клиента, без документа, неоднозначность — обрабатываются штатно.

При ошибке чтения или расчёта новые результаты не записываются; файлы прошлого запуска остаются. Запись двух файлов не является транзакцией: сбой во время сохранения может оставить неполный вывод.

### Задача 1

**Масса.** Независимое округление трёх равных долей 1 т даёт `0,3 + 0,3 + 0,3 = 0,9` т. Выбрано сохранение итога методом наибольших остатков: целые десятые распределяются вниз, оставшиеся — частям с наибольшими дробными остатками; при равенстве приоритет у более ранней части. Получается `0,4 + 0,3 + 0,3 = 1,0` т: разница учтена, а не потеряна. Альтернатива — исправлять последнюю часть — накапливает в ней поправки и может сделать её отрицательной. Это учётное распределение, а не измерение массы отдельных вагонов. Если исходная масса точнее 0,1 т, сначала округляется общий итог по `ROUND_HALF_UP`; сумма частей сохраняет именно этот итог.

**Период.** Начальный и конечный день включаются целиком: ограничение концом дня в 00:00 исключало бы вечерние отправки последнего дня. Просроченная заявка продолжает принимать вагоны, будущая — не принимает: это прямо следует из правила 5. Время поступления и отправки сохраняется для сортировки.

**Равные приоритеты.** При совпадении обеих дат очереди заявок сохраняется входной порядок; аналогично при одинаковом времени отправки накладных. Другой критерий не задан, а номер заявки прямо запрещён как приоритет. Перестановка равнозначных входных строк может изменить результат.

**Превышение.** На пару «заявка — накладная» выводится одна строка: общий объём в `vagonov` и `massa_t`, количество из него сверх заявки — в `sverh_zayavki`. Например, B2002: 10 вагонов, 570 т, из них 2 вагона сверх. Отдельные строки дублировали бы номер без необходимости: обычное количество равно `vagonov − sverh_zayavki`. Объединение выполняется до распределения массы, чтобы округление не зависело от внутренних этапов алгоритма. Между разными заявками накладная по-прежнему делится.

**Пустые значения.** Отсутствующий, пустой или `null` клиент накладной означает `bez_klienta`; у активной заявки клиент обязателен. Активные заявки без распределения выводятся с пустым списком, чтобы отличать их от исключённых. Группы `bez_zayavki` создаются только при наличии остатков.

### Задача 2

**Повторные позиции.** Строки одного кода суммируются внутри одной записи журнала или одного документа: `2 + 3` равны `5`. Альтернатива — сравнивать отдельные строки — отвергала бы одинаковое общее количество одного материала только из-за разбиения. Разные документы или записи не объединяются.

**Один документ для нескольких записей.** По условию «неоднозначно» означает несколько подходящих документов для одной записи. Обратная ситуация — несколько записей претендуют на один документ — отдельно не определена. Выбран порядок по дате записи, затем по числовому ID: первой закрывается более ранняя выдача. Кандидаты ищутся среди ещё не использованных документов, поскольку повторная связь запрещена. Поэтому первая запись с единственным кандидатом связывается, а следующая, если свободных кандидатов больше нет, попадает в `ne_najdeno`. Здесь «не найдено» означает отсутствие подходящего доступного документа. Альтернатива — не связывать обе записи — вводила бы отдельный вид конфликта сверх описанного в условии. Порядок по дате и ID остаётся выбранным допущением, а не прямым требованием.

**Несколько документов для записи.** Запись остаётся неоднозначной, документы не резервируются. Повторного поиска после обработки остальных записей нет: он добавил бы автоматический выбор через исключение кандидатов, которого условие не требует. Список отражает кандидатов на момент обработки; один из них впоследствии может связаться с другой записью.

**Возвраты.** Для `vozvrat` не задан вид документа 1С, поэтому активный возврат входит в `ne_najdeno` и корректирует остатки. Исключать его из отчёта означало бы скрыть движение без подтверждённой связи. Непустой `kontragent_id` означает возврат от подрядчика, иначе — от своих. Карточка не восстанавливается по `iskhodnaya_id`: правила такого восстановления не заданы. Ссылка на исходную выдачу не подтверждает проведение самого возврата в 1С.

**Статусы.** Только `vydano` участвует и в связывании, и в корректировке остатков. Для связывания это требование, для расчёта — выбранная трактовка: отменённые и черновые записи не подтверждают фактическое движение.

**Остатки.** Строки суммируются по МОЛ/коду или контрагенту/коду; отсутствующая пара начинает с нуля. Это предполагает, что отсутствие строки означает нулевой запас, а не неполную выгрузку. Отрицательные результаты сохраняются для сверки: обнуление скрыло бы величину расхождения. Нулевые строки убираются только у подрядчиков. Связанные выдачи повторно не учитываются, несвязанные, включая неоднозначные, изменяют остатки по формуле задания.

**Границы данных.** Используется весь снимок: дата отсечения не задана, отбор по сегодняшней дате мог бы исключить старые незакрытые выдачи. Неизвестный тип активной записи журнала вызывает ошибку; неподдерживаемый вид документа 1С не является кандидатом. Счёт `10.07` относится к подрядчикам, остальные — к МОЛ; пустой контрагент на этих остальных счетах допустим. МОЛ, коды и карточки сравниваются точно, одинаковые имя или ИНН не объединяют карточки. Окно даты документа включительно: от −2 до +14 дней относительно записи.

## Технические решения

- Названия данных сохранены из задания: `zayavki`, `nakladnye`, `zhurnal`, `dokumenty`, `kontragent_id` и другие. Обычно я придерживался бы стиля проекта, но здесь он неизвестен: исходные названия избавляют от запоминания нескольких терминов для одних данных. Вспомогательные имена — английские (`queue`, `parts`, `candidates`). Вычисляемые остатки различаются: `available_wagons` — свободные места заявки, `unallocated_wagons` — нераспределённые вагоны накладной.
- Расчёты отделены от чтения и записи файлов; входные словари не изменяются.
- Арифметика и сравнение количеств выполняются через `Decimal`. Запятая заменяется точкой, дробные JSON-числа читаются сразу как `Decimal`. На выходе используется `float` для числового JSON; после этого вычислений нет. Остатки не округляются до десятых. Решение рассчитано на точность чисел задания, а не на произвольно длинные десятичные значения.
- `nachalo` и `konec` принимают `дд.мм.гггг` и `дд.мм.гггг чч:мм:сс`: время проверяется, затем используется только день. `postupila` и `data_otpravki` требуют дату со временем и сохраняют его; даты второй задачи имеют формат `гггг-мм-дд`.
- Проверяются уникальность идентификаторов, конечность чисел и период заявки. Вагоны — целое число: у заявки допустим ноль, у накладной требуется положительное количество. Строки движений должны содержать положительные количества и непустой состав; нулевые строки не трактуются как движение.
- Для каждого клиента сохраняется позиция продолжения заполнения заявок, чтобы не проходить заполненное начало очереди заново. Поиск заявки для превышения остаётся обратным проходом.
- Документы индексируются по виду, МОЛ, карточке и составу. Внутри группы они сортируются по дате: двоичный поиск выделяет допустимый период, затем проверяется занятость документов. Справочники использованы для анализа данных, расчёт опирается на коды и ID движений.

## Проверки

Тесты написаны на стандартном `unittest`. Проверены на Python 3.13.5; отдельный запуск под 3.10 не выполнялся, код использует синтаксис и API, доступные в 3.10.

| Правило задачи 1 | Тесты в `tests/test_task1.py` |
| --- | --- |
| 1. Отозванные исключаются | `test_rule1_withdrawn_applications_are_excluded` |
| 2. Клиенты разделены | `test_rule2_clients_do_not_share_capacity_or_overflow` |
| 3. Очередь по началу и поступлению | `test_rule3_start_date_has_priority_over_received_date`, `test_rule3_received_date_breaks_tie_not_number` |
| 4. Порядок отправки | `test_rule4_invoices_sorted_by_timestamp` |
| 5. Начало периода и добор просроченной заявки | `test_rule5_future_application_cannot_accept`, `test_rule5_expired_application_filled_before_current` |
| 6. Разделение и округление массы | `test_rule6_invoice_split_and_mass_preserved`, `test_mass_rounding_uses_largest_remainders_and_stable_ties` |
| 7. Превышение в последнюю подходящую заявку | Три теста с префиксом `test_rule7_` |
| 8. Без заявки и без клиента | Два теста с префиксом `test_rule8_` |

Для задачи 2 проверены виды документов, МОЛ, карточки контрагентов, состав позиций, границы дат, статусы, неоднозначность, однократное использование документа, возвраты, знаки корректировок, точная десятичная арифметика и нулевые/отрицательные остатки. Интеграционные тесты сравнивают оба полных JSON с вручную рассчитанными ожиданиями, проверяют повторный запуск и ошибки входных файлов.

## Результат на выданных данных

- Заявка `0000700188` получает 30 вагонов, `0000700120` — 40, `0000700310` — 7; A1005 делится на 7 и 7 вагонов по 413 т.
- Заявка `0000700050` получает 20 обычных вагонов и 2 сверх заявки; `0000700333` — 9, `0000700400` — 5. G3001 остаётся без заявки, X9001 — без клиента.
- Связи: `1 → d-101`, `3 → d-103`, `6 → d-105`. Не найдены: `2, 5, 8`. Неоднозначность: `4 → [d-106, d-107]`.
- Остаток Н-003 у Кузнецова: `27.31 − 15.9 = 11.41`; Н-002 у Петрова: `12 − 4 + 1 = 9`; Н-002 у k-3: `8 + 4 − 1 = 11`.

## Что насторожило и что сказать кладовщице или бухгалтерии

1. Карточки k-1 и k-2 имеют одинаковые имя и ИНН: проверьте дубликат справочника; автоматически их не объединяю.
2. Для записи 2 документ d-102 датирован на 20 дней позже: сверьте даты и задержку проведения; окно +14 дней не расширяю.
3. Для записи 4 подходят d-106 и d-107: проверьте, не задвоена ли передача, и укажите правильный документ.
4. Возврат 5 связан с выдачей 4 только через iskhodnaya_id: нужен отдельный вид и идентификатор документа возврата 1С.
5. Запись 8 от 31.03.2026 значительно старше остальных: проверьте дату, незакрытую выдачу и полноту выгрузки документов.
6. У несвязанных выдач могут уже быть движения в остатках 1С: расчёт по заданной формуле требует ручной сверки записей 2 и 4.
7. Дата снимка остатков не указана: согласуйте её с датой отсечения журнала и выгрузки документов.
8. X9001 без клиента, а G3001 отправлена до начала заявки: заполните клиента и проверьте основание ранней отправки.
